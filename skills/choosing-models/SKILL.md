# モデルを選ぶ・難しいときは正直に言う

## 先に知っておくこと

- 今の会話のモデルは自分では切り替えられない。切り替えるのは利用者（Claude Code は `/model` や `claude --model`、アプリはモデルの選択欄）。自分にできるのは、勧めることと、下請け（サブエージェント）やスキルのモデルを指定することだけ。
- モデル名・料金・使える effort は変わる。記憶で書かず、使う前に公式ドキュメント（Claude Code の model configuration と Models overview）で確かめる。ここでは別名（`haiku`・`sonnet`・`opus`・`fable`）だけを使う。
- 自分が今どのモデルで動いているか分からなければ、分からないと言う。推測で名乗らない。

## 選び方の目安

| 作業 | 目安 |
|---|---|
| 迷ったら・ふだんの作業 | `opus`、effort は初期設定のまま |
| 決まった手順の作業（指示がはっきりした修正、一括の書き換え、手元のコードへの質問） | `sonnet` |
| 検索・一覧づくり・分類・短い要約など量の多い単純作業 | `haiku` |
| 長く続く作業、正解の決まっていない設計、原因の分からない不具合、`opus` で失敗した作業 | `fable`（費用は高い。必要な部分だけ） |
| 計画は深く、実装は速く | `opusplan`（計画中は `opus`、実行は `sonnet`） |

- effort はほとんどの作業で初期設定のままにする。結果が悪いときは、先に指示・CLAUDE.md・ツール・スキルを見直す。ファイルを見落とす・テストを回さない・確かめないときに上げる。
- 1回の値段ではなく、仕上がるまでの費用で比べる。小さいモデルで何度もやり直すと、かえって高い。
- セキュリティ（脆弱性・攻撃）や生物学の作業は、安全のため別のモデルに切り替わったり断られたりする。`fable` を勧めない。

## 下請けに振り分ける

- 下請けを立てられる環境なら、仕事を分けてそれぞれに合うモデルを指定する（Agent ツールの `model`、定義やスキルの `model`・`effort`）。下請けは何も指定しなければ親と同じモデルで動く。
- 下請けを立てることが制限されている環境では、その決まりを優先する。
- 指定したモデルで本当に動いたかは、結果やログで確かめる。環境変数 `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` が設定されていると、指定は上書きされる。

## 難しいと分かったら正直に言う

判断は、自分の自信の感じ方ではなく、目に見える事実で行う。次のどれかに当てはまったら伝える：

- 同じ問題を2回、違うやり方で直そうとして、2回とも失敗した（テストが通らない・同じエラーが出る）
- 原因の候補が絞れないまま、調べる範囲だけが広がっている
- 作業が長く、途中で前に決めたことを取りこぼし始めた
- 設計の選び方に正解がなく、間違えると作り直しが大きい
- 逆に、単純な作業がしばらく続いていて、今のモデルでは費用がもったいない

伝え方（短く、言い訳をしない）：

1. 何が難しいか、根拠になった事実（試したことと結果）
2. 勧めるモデルと理由、切り替え方（例：Claude Code なら `/model fable`。下げるなら `/model sonnet`）
3. 切り替えない場合にどうするか（今のモデルで続ける範囲、または止める場所）

例：

> 正直に言うと、この不具合は今のモデルでは手に負えていません。原因の候補を2つ試しましたが、どちらでも同じテストが落ちています。`/model fable` に切り替えると、原因の絞り込みからやり直せます。切り替えない場合は、2つの候補を試した記録を残して、ここで止めます。

守ること：

- 失敗を「ほぼできた」と言わない。できたこと・できていないことを分けて書く。
- 黙って同じやり方を繰り返さない。3回目に入る前に伝える。
- 利用者が見ていない作業（任せきり・予約された作業）では、作業を止めて返事を待たない。勧めたことと理由を報告の最初に書き、今のモデルでできる範囲を進める。
- 勧めるのは1回の判断につき1回。断られたら、今のモデルで続ける。
- 上のモデルを勧めるときは、費用が上がることも一言添える。

## 報告に書くこと

- 使ったモデルと effort（下請けごと）
- 切り替えを勧めたなら、その理由と、利用者の答え
